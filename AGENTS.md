# AGENTS.md — Mova

These instructions are for AI agents (and people) working on Mova.

**First read `docs/mysticism/02-gali.md` and enter the mode.** It is a working mode for an AI that builds with a human operator: Mova's own working philosophy, not tooling; nothing in the build or the checks depends on it. Do not just skim it: step in and work.

---

## What Mova is

Mova is a Hybrid Combinatorial–Operational System written in Rust, with a Combinatorial Small Language Model at its core and recursive use of its own capabilities. Its language layer parses English into Universal Dependencies trees, frames and a world; its combinatorial layer describes and compares models and checks; its operational layer concretizes supported tasks and coordinates workers. Keep native inference, optional external consultants and reviewed training separate. A large model never answers Mova's assessment questions for it. Start with `README.md`, `docs/architecture.md` and `docs/hybrid-system.md`; preserve their explicit implementation limits.

## Working rules

- **Project identity (2026-11-02).** Introduce Mova as a Hybrid Combinatorial–Operational System with a Combinatorial SLM at its core and recursive use of its own capabilities; the mascot is an octopus. In the project the 🐙 Octopus is a large language model (LLM), most often Claude Opus, that develops and coordinates Mova; Mova's own animals (Crab, Eel, Fish, Whales, Sea Spider) are Rust on Mova — see `docs/animals.md`. See `docs/hybrid-system.md`. Distinguish implemented scope from architectural direction. Preserve dated measurements and stable technical identifiers when updating presentation.
- **English everywhere** in code, comments, docs, commit messages and data. Talk to the operator in their language.
- **Mechanics in Rust.** Code chews the data, not your tokens. Avoid bash or Python improvisation; the few Python bridges, to the neural parsers and the pragmatic witnesses, are the exception.
- **Compose from what exists.** Grep the repo before you write new code.
- **Deterministic.** Use `BTreeMap`/`BTreeSet` wherever order decides anything. Before you claim a gain, run twice and check the two runs are identical.
- **Measure before you claim.** Keep held-out sets held out: the SVAMP test runs once per release, and decisions are made on the two-fold check (`cv`). State every number with its date.
- **Negative control.** A gate that cannot show red is not a gate.
- **Training teacher: Codex CLI via `mova-teacher`, authenticated with ChatGPT.** Claude API is no longer used for training. Never fall back to it; preserve old results as history. New queues use the configured Codex model and fresh run directories (`docs/training.md`, current teacher transport).
- **Model defaults (2026-11-04).** Every animal that calls an LLM (Whales, Dolphins, Nautilus, Sea Turtle) defaults to Opus; Fish default to Sonnet. Where needed, Sol (`gpt-6.1-sol` via Codex CLI) may replace Opus or Sonnet; for Fish, Terra (`gpt-6.1-terra`) is recommended. The consultant Dolphin and the Octopus may also be Fable (`claude-fable-5-1`) or Astra (`gpt-6-astra`). The public Fish pool defaults to 2 workers, the recommended minimum; more may run, up to the supported maximum of 8. See `docs/animals.md`.
- **Concrete Fish annotation profiles (2026-11-04).** New AST/pragmatics preparation defaults to Sonnet through an explicit CLI/terminal profile; Terra (recommended), Sol and Haiku remain configurable alternatives. Rendered requests are bounded to 100000 UTF-8 bytes including wrappers. Concrete deployments keep overrides outside public source. Preparing a request or GPU-admission candidate does not execute a teacher or authorize training; no Claude API fallback is implied.
- **Fail-fast.** No blind retries on expensive steps. New directions and expensive runs (large-model batches, long trainings) need the operator's explicit word.
- **GPU throughput priority (2026-10-29).** Training speed and test-pass speed take priority over byte-identical GPU results. Small measured numerical or task-score deltas are acceptable; report them. Preserve valid outputs and correct training gradients. Keep a reference switch for comparisons.
- **Fast development measurements (2026-10-29).** Use `world knowledge bench` for iterative school measurements and `GP_DEV_EVERY=5 GP_DEV_QUICK=256` for multi-epoch training probes; run larger and full checks periodically. Do not require the full suite on every small timing experiment. Keep probe scope and skipped checks explicit, with full measurements for confirmation.
- **Per-file and hierarchical models (2026-10-29).** Every owned Rust file needs a description, forward approximant, separate reverse/complementary approximant, invariant, cost approximation and simple checks. A block of the same `model.md` describes the mathematical combiner and retains its own useful observations from previous modeling epochs; inputs include Rust/AST and the models/descriptions; selected file groupants contain source-bound partial Rust syntax projections; macro expansion and semantic AST analysis remain absent. The reverse-reconstruction type models undoing transformations or recovering compatible antecedents from a result: use preimage/converse relations, with unique recovery only under appropriate injectivity assumptions. Exclusion tests alone do not implement it; see `docs/mathematical-modeling.md`. Groups need interaction models at progressively higher abstraction levels in a tree; correct leaves do not prove their wiring. Register changed/new files in `models/contracts.json`, run `mova-modelcheck changed REPO REGISTRY BASE NEW_JSON`, and run the relevant checks. Keep unknown behavior and missing legacy coverage explicit; a registry entry is not verification. Preserve prospective predictions and update models from real Rust measurements. See `docs/mathematical-modeling.md`.
- **Groupants (2026-10-29).** A code-associated combinator node is a groupant with core components: AST, forward approximant, typed obernant family, invariant and descriptant (Markdown description/epoch memory). Groupants are extensible and may also hold tests and any useful extra material. Store per-file contents in the adjacent `<filename>.groupant/` directory (for example `main.rs.groupant/`): one Markdown file, `model.md`, with blocks (`## descriptant`, `## model`, `## tests`, … sections) beside `manifest.json`, which references them as `model.md#Section` (operator, 2026-11-04; `mova-modelcheck consolidate`); keep the authoritative raw source in its original file. A complex file groupant may recursively contain child groupants inside its adjacent sidecar, with explicit source scopes and parent composition models. The system is modeled as a tree of groupants; parents model larger interactions at higher abstraction. Preserve missing components as explicit gaps; see `docs/groupants.md`.
- **Executable Rust approximants (2026-10-30).** Add executable Rust surrogates alongside mathematical groupant models where a useful observation metric exists. Supported error caps are 1%, 2%, 5% and 10%; lower actual error is welcome and no budget above 10% is supported. Classify each executable profile by metric, approximation method and assurance kind; finite observations must not be promoted to analytical guarantees. Bind code, exact source and evidence hashes, define domain/metric/zero behavior, distinguish analytical bounds from finite observed error, preserve invariants, and measure against the real reference. Keep unsupported semantics explicit; no automatic production substitution or unproved composition-wide bound. When building a vidtvorant or an obernant, read the original's program code first, then confirm with observations. See `docs/mathematical-modeling.md`.
- **Math-first reviews (2026-10-29).** Before an optimization, state the model, invariants and expected cost change. Explore approximations and derivatives cheaply; use Rust for implementation and real timing, with focused correctness checks and periodic larger/full validation. Review existing algorithms for implementation bugs as well as new ideas. Save prospective predictions and use measurements to correct them; a Lean proof alone does not establish runtime or task accuracy.
- **Knowledge placement (2026-10-29).** Understanding mechanisms and hard parameters belong to the revisable skeleton and change chiefly through deliberate code/model updates and retraining. The global graph durably records human and AI-derived knowledge; the important graph is operationally useful logical/informational knowledge in RAM. These are nonexclusive: compilation/activation never removes global provenance, and controversy alone does not imply RAM residency. Preserve derivation premises, scope, alternatives and revisions; see `docs/knowledge.md`.
- **Persistent school learning (2026-10-29).** Lessons must yield retained graph knowledge, learned parameters or general skeleton changes. Replaying a lesson at test time is a reading diagnostic, not persistent learning. Evaluate in a fresh process from a saved state and question-only input, with no lesson focus or updates. Keep assessment labels outside training; use failures to diagnose representation, inference or parameter problems. See `docs/school.md`.
- **Mova-driven improvement (2026-10-29).** Use `mova-enrich improve` for a bounded study/propose/review/learn/assess step. Teacher context uses exercise feedback only; preserve frozen assessment sources and current dictionary meanings. Reuse already retained material, compare the same questions before/after, and measure old-knowledge regression. Extra frames or different test scores alone are not improvement. See `docs/school.md`.
- **Corpus enrichment (2026-10-29).** Annotation/training alone does not complete dictionary, lesson or exam enrichment. Feed agreed syntax, pragmatics and context into Mova proposals and the Codex teacher. Keep source/version evidence, artifact states and failures; never mark a whole pass seen after partial failure. Narrative-driven factual additions need independent evidence. Explore queue/cost ideas mathematically before bounded real runs; section 24 of docs/training.md describes the experimental mode.
- **Two execution modes** (`docs/gpu-exec.md`). **CPU only** is the default and is exact. **GPU enhanced** needs `--features gpu` and `MOVA_EXEC=gpu`. A GPU stage is exact (gated byte for byte) or an approximant (its agreement measured and reported).
- **Licences of data** (`licence/DATA.md`):
  - code only: the Elamur Cosmic License (`LICENSE.md`);
  - data products (dictionaries, corpora, models, tables): CC BY-SA 4.0 (or a source's stricter licence), each in its own folder with a `LICENSE.md` that cites every source; use whatever data is needed and cite it;
  - NC and research-only data: only for tests and measurements, never in what is built.
- **Data lives outside the repo**, in `$MOVA_DATA`, and so do run results. The repo holds code, rules, seeds and small data.
- **Parallel agents work in their own worktrees.** Use `git worktree add <scratch>/<task> -b <task> main`, and point all of them at one shared `CARGO_TARGET_DIR` (a release target per task takes tens of GB and fills the disk). Crates depend on `en` by path, so an edit in a shared copy breaks the others' builds. The main instance merges.
- **Knowledge goes into the repo** (`docs/`, crate READMEs). Keep docs plain: what it is, how it works, how to run it, limits. Docs describe how things are; they do not argue with numbers.
- **Fewer, better documents (2026-11-04).** New documentation extends an existing document (see `docs/README.md` for the set). A new `docs/` file needs a reason: a new subsystem. Call the model the SLM in English text.
- **Typed obernant families (2026-10-29).** Every file/group/subsystem/root groupant must account for behavior_complement (an approximant of what the system does not do) first, and reverse_reconstruction (output to compatible inputs/states) second, plus useful typed/specialized variants. Record missing models explicitly. Negative tests alone do not supply the first model; inverse laws apply only to the appropriate type. See docs/mathematical-modeling.md.
- **Current descriptions.** State current names, mascots and routine design choices directly; do not narrate their rename history. Preserve scientific evidence and useful modeling-epoch observations.
- **External reference-groupant library (2026-11-01).** General algorithm explanations and scholarly-work groupants live outside Git in `$MOVA_GROUPANTS`, with no Git repository in the collection. Keep Mova-specific development groupants adjacent to their Rust sources. Seed paper nodes from works actually used by code, with explicit access/formalization gaps. See `docs/groupants.md`. Do not repopulate root `groupants/` with the collection or silently refresh stale hashes.
- **Publication scope (2026-11-01).** Mova code-associated groupants, external copies/snapshots and implementation-use paper models are not global website content. A hash-bound publication catalog must explicitly admit independently reviewed global expositions through entries[].library_scope=global, editorial/rights checks and an approved artifact list. Missing/unreviewed/stale scope is excluded. Do not bulk-promote code wrappers or refresh historical bindings to make them publishable. Preserve immutable research references; see docs/groupants.md. Groupant pages are published on groupants.elamur.ai (Mova code models as their own section), never on the mova site.
- **Nothing private in the repo.** No private paths, personal names or secrets in code, docs or data.
